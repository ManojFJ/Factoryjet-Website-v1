# /_next/ holds build internals we do not want crawled, EXCEPT /_next/static/,
# which is where the JS and CSS a crawler needs to render the page live.
# Blocking all of /_next/ cost us 3,714 refused bingbot fetches in the 30 days
# to 2026-08-03 (165,541 in March) — measured via pipeline/research/bing_webmaster.py.
# Our pages are statically generated so the text survives an unrendered fetch,
# but Bing renders worse than Google and there is no upside to refusing it.
# Allow precedes Disallow so first-match crawlers also resolve it correctly;
# Google and Bing both take the longest match regardless of order.
# No /_next/image rule needed: next.config sets images.unoptimized, so the
# optimizer endpoint is never used and images serve from /images/... directly.
Allow: /_next/static/
Disallow: /_next/

# ─── AI TRAINING bots we deliberately ALLOW ───
# RESOLVED 2026-09-09 by Bhavesh: option (a). The Content-Signal line above now
# reads ai-train=yes, which matches the three Allow rules below. Declared policy
# and actual behaviour agree again.
#
# WHY allow training: FactoryJet sells AI visibility. A model that absorbed our
# pages during training can name us with no retrieval step at all, which is the
# cheapest form of the exact outcome we sell. We host nothing on this domain that
# is worth withholding from a model, so there is no cost on the other side.
#
# This is NOT a blanket ai-train=yes for everyone. Access control (the Disallow
# rules below) and usage permission (Content-Signal) are separate layers: we grant
# the permission generally, then refuse access to the data brokers in the next
# section. First-party vendor crawlers whose models we want to reach = allowed.
# Third parties who scrape to resell a corpus = still blocked.
